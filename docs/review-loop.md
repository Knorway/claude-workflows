# 구현 → 리뷰 → 수정 루프를 자동화하기

`/wt:review`가 왜 지금 모양인지, 그리고 더 밀고 싶을 때 무엇을 어떻게 바꾸면 되는지.
사용법은 [플러그인 README](../plugins/wt/README.md)에 있다.

## 1. 자동화하려는 것은 "리뷰"가 아니라 "독립성"이다

원래 흐름은 이랬다: 한 세션이 구현해 PR을 올리고, 사람이 **탭을 하나 더 열어** 문맥이
전혀 없는 새 세션에 리뷰를 시키고, 결과를 구현 세션에 붙여넣어 고친다.

이게 작동한 이유는 리뷰어가 구현자의 추론을 **하나도 물려받지 않기** 때문이다.
실제 사례 — PR #28에서 프로젝트 설정에 `extraKnownMarketplaces` 선언이 빠져 있었다.
구현 세션은 이걸 볼 수 없었다. 그 머신에는 사용자 스코프에 같은 마켓플레이스가 이미
등록돼 있어서 **증상이 나타나지 않았고**, 구현자는 "동작하니까 맞다"는 증거를 손에
쥐고 있었다. 새 세션은 그 증거가 없으니 설정 파일만 보고 빠진 걸 알아챘다.

따라서 자동화의 목표는 **탭을 여는 수고만 없애고 독립성은 그대로 두는 것**이다.
구현한 세션이 자기 diff를 다시 읽는 방식은 아무리 프롬프트를 세게 써도 이걸 못 준다.

## 2. 독립성에는 등급이 있다

| 방식 | 리뷰어가 보는 것 | 독립성 | 비용/지연 | 누가 띄우나 |
| --- | --- | --- | --- | --- |
| 같은 세션의 자기검토 | 구현자의 추론 전부 | 없음 | ~0 | 모델 |
| **서브에이전트** (`/wt:review`) | 호출자가 준 프롬프트 + 자기가 읽은 diff | 중상 | 수만 토큰, 수십 초 | 모델 |
| **별도 프로세스** (`claude -p`) | diff + 레포 규약(자기가 읽음) | 상 | 세션 1회분 | 스크립트/사람 |
| **`claude ultrareview`** | 브랜치·PR 전체, 클라우드 다중 에이전트 | 최상 | 비쌈, 수 분 | **사람만** |
| **GitHub Actions** | PR diff, 로컬 상태 없음 | 최상 + 비동기 | CI 실행비, 수 분 | 이벤트 |

서브에이전트의 독립성이 "최상"이 아닌 이유는 하나다: **프롬프트와 diff 범위를
구현자가 정한다.** 구현자가 무의식적으로 좁게 잡으면 리뷰어는 그 안만 본다. 그래서
`/wt:review`는 렌즈를 고정 문구로 박아두고, diff를 요약해서 넘기지 않고 **명령을
넘겨 리뷰어가 직접 읽게** 한다.

`claude -p`로 한 단계 더 올릴 수 있다 — 진짜 별개 프로세스라 훅·`CLAUDE.md`·설정을
스스로 로드한다. `--json-schema`로 구조화 출력, `--max-budget-usd`로 상한을 걸 수
있다. 대신 세션이 통째로 하나 더 뜨는 값이고, 인증·권한 모드를 따로 챙겨야 한다.
서브에이전트로 충분치 않다고 느낄 때 올리면 된다.

## 3. 언제 발화시킬 것인가

| 시점 | 방법 | 성격 |
| --- | --- | --- |
| **명령형** | `/wt:review` | 사람이 원할 때만. 되돌리기 쉽고 비용이 예측 가능 |
| **푸시 게이트** | `/wt:remote-push` 4단계와 5단계 사이에 삽입 | 리뷰를 잊을 수 없음. 대신 푸시가 매번 느리고 비쌈 |
| **세션 종료 게이트** | `Stop` 훅이 `{"decision":"block","reason":…}` 반환 | 모델이 그냥 못 끝냄. 강력하지만 빠져나오기 번거로움 |
| **CI** | PR `opened`/`synchronize` 이벤트 | 노트북을 닫아도 돌고 기록이 PR에 남음 |

지금은 **명령형만** 만들었다. 나머지는 명령형이 실제로 쓸 만한지 확인한 뒤에 올리는
게 맞다 — 게이트를 먼저 달면 리뷰 품질이 나쁠 때 워크플로 전체가 인질이 된다.

## 4. 비용은 에이전트 수가 아니라 "수 × 각자가 읽은 양"이다

| 요인 | 영향 | `/wt:review`의 대응 |
| --- | --- | --- |
| diff 크기 | **가장 큼.** N명이 같은 diff를 각자 읽으므로 N배 | 오케스트레이터 문맥에는 `--stat`만. 원문은 서브에이전트 안에서만 존재 |
| 리뷰어가 여는 파일 | 큼. 파일 전체는 diff의 수십 배 | "diff가 근거를 못 주는 곳만 열어라" + `Grep` 우선 |
| 렌즈 수 N | 선형 | diff <200줄이면 2, 기본 3, 조건 충족 시 +인터페이스 렌즈 |
| 반증 표 수 | findings × 표 | **항상 1표.** 같은 기반 모델을 여러 표 쌓아도 오차가 상관되어 표 수만큼 정확해지지 않는다 |
| 테스트 작성 | 러너 있는 레포에서만 +1 | 자기가 쓴 파일만 돌린다. 전체 스위트는 `wt-verify`에서 한 번 |
| 테스트 래칫 | **0** | 에이전트가 아니라 오케스트레이터의 `git diff --numstat` 1회 |
| 라운드 수 | 곱 | 수정 세대 **최대 2회**(5단계·재검토 통틀어) |

직관에 반하는 결론 하나: **렌즈를 하나 더 붙이는 것보다 파일을 마구 여는 리뷰어
하나가 더 비싸다.** 그래서 프롬프트의 비용 규칙이 렌즈 수보다 중요하다.

**실측** — 1,000줄 규모 PR(플러그인 추출 PR #28)을 렌즈 2·반증 0으로: **$2.45 / 331초.**
지금의 기본값(렌즈 3 + finding당 반증 1)이면 대략 그 1.5~2배.

그리고 **에이전트 수로 비용을 예측하지 마라.** 2,625줄 diff를 두 번 돌린 실측에서
1회차는 에이전트 9개에 399k, 2회차는 **8개에 477k**였다 — 에이전트가 줄었는데 20% 비쌌다.
위 표의 첫 두 행이 지배한다는 뜻이고, 그래서 이 문서는 렌즈 수를 사람이 고르게 하지 않고
diff에서 유도하는 쪽으로 갔다.

가장 큰 절약은 **diff를 오케스트레이터 문맥에 올리지 않는 것**이다. 올리면 그 토큰이
이후 대화 내내 매 요청에 다시 실려간다. 서브에이전트 문맥은 끝나면 사라진다.

## 5. 완전 자동 루프를 고르지 않은 이유

리뷰 → 수정 → 재리뷰를 findings 0까지 도는 건 기술적으로 된다. 실제로 겪는 문제는
아래 여섯이고, 앞의 둘만 *진단*에 대한 것이다 — 나머지는 전부 **수정하는 쪽**에서 나온다.

- **리뷰어의 오판이 그대로 코드가 된다.** 직전 PR #28 리뷰 5건 중 1건은
  `set -e` 규칙을 잘못 안 오탐이었고, 재현 실험으로 반증했다. 자동 루프였다면
  멀쩡한 코드가 "고쳐졌을" 것이다.
- **거르는 쪽도 같은 방식으로 틀린다.** 이 커맨드를 만들고 바로 그 오탐을 반증
  담당에게 물려봤더니 `CONFIRMED`가 나왔다. 이유는 자기 출력에 적혀 있었다 —
  샌드박스가 `bash -c`를 막아 **재현을 못 하자 기억 속 규칙으로 추론**한 것이다
  (실제 bash 3.2에서는 죽지 않는다). 그래서 두 겹으로 막았다: 프롬프트에
  "실행으로 확인 못 했으면 CONFIRMED 금지", 그리고 오케스트레이터가 `check`가 빈
  `CONFIRMED`를 **기계적으로 PLAUSIBLE로 강등**. 판정을 모델의 선의에 맡기지 않는다.
  (부작용 하나: 헤드리스/샌드박스 환경에서는 서브에이전트의 셸 실행이 막혀 재현이
  거의 불가능하므로 `CONFIRMED`가 잘 안 나온다 — 자동 수정이 적게 발화한다는 뜻이고,
  틀리는 방향으로는 안전한 쪽이다. 대화형 세션에서는 정상적으로 재현한다.)
- **처방자의 오판은 아무도 안 본다.** 위 둘은 *진단*에 대한 장치다. 그런데 진단 게이트를
  세게 걸수록 **잔여 오류의 지배적 출처가 처방자로 이동한다** — 수정을 하는 것은 문맥을
  다 가진 오케스트레이터이고, 그 산출물에는 게이트가 하나도 없다.
  실측: 2,625줄 diff를 두 번 리뷰했더니 **2회차 지적 6건 중 3건이 1회차의 수정이 만든
  것**이었다. 한쪽 경계만 고친 절반짜리 수정 하나, 그리고 주석에 **사실이 아닌 규칙을
  써넣은 것** 둘(그중 하나는 규약 문서에 착지해 다음 라운드의 근거가 될 뻔했다).
  그래서 지금은 (a) 규약 문서를 자동 수정 대상에서 빼고, (b) 수정이 추가한 산문을
  보고에 **원문 그대로** 따로 싣고, (c) 수정분 재검토를 **맥락 없이** 한다.
- **검증 자체를 무르게 하는 수정.** 처방자 오판의 특수형인데 증상이 정반대다. 보통의
  오판은 검증 사다리가 **빨갛게** 잡아주지만, 이 부류는 사다리를 무르게 만들어서
  **초록이 된다** — 단언을 지우거나 약화하고, `.skip`을 붙이고, 러너의 `exclude`·
  `retries`·`continue-on-error`를 넓힌다. 자기를 검사할 도구를 자기가 고치는 것이라
  **관측이 스스로를 못 잡는다.**
  누가 저지를 수 있는지를 보면 대응할 자리가 정해진다: `wt:test-writer`는 프로덕션 쓰기
  금지·기존 테스트 수정 금지로 이 파이프라인에서 가장 강하게 묶여 있고, **아무 제약이
  없는 것은 5단계의 수정자**다. 감시할 대상은 테스트를 쓰는 쪽이 아니라 고치는 쪽이다.
  그래서 여기만 유일하게 **구문적 지문**에 기댄다 — 지워진 줄 수, `skip`, 러너 설정 변경은
  `git diff --numstat` 한 줄로 보인다. 정당한 경우(공허한 단언을 고치는 것)와의 구분도
  기계적이다: **그 테스트 파일을 지목한 CONFIRMED가 있느냐.** 감시자 에이전트를 두지
  않은 이유는 두 가지다 — 서브에이전트는 서로의 도구 호출을 볼 수 없어 "감시"가 결국
  사후 diff 감사로 환원되고, 그 감사에 같은 기반 모델을 쓰면 "이 단언은 과도했으니 완화가
  정당하다"는 판단을 심사자가 똑같이 납득한다(위 항목과 같은 상관 오차).
  **적발해도 되돌리지는 않는다.** 이 루프는 커밋되지 않은 사용자 수정을 안고 돌기 때문에
  롤백은 리뷰와 무관한 작업까지 지운다. 대신 보고에 숫자를 그대로 싣고 원장을 `human`으로
  내려 푸시 게이트를 닫는다.
- **churn — 원천이 둘이다.** 하나는 기억 부재: 리뷰어는 매 라운드 새 문맥이라 이전
  라운드에서 기각된 지적을 다시 낸다. 다른 하나는 위 항목: 수정이 새 결함을 만들어
  **정당한** 새 지적을 낳는다. 둘은 증상이 같고 처방이 다르다 — 앞엣것은 기억이,
  뒤엣것은 수정 검사가 필요하다. 하나로 묶어 보면 틀린 쪽을 고치게 된다.
- **비용이 곱으로 늘어난다.** 라운드마다 렌즈 × diff이고, diff는 수정할수록 커진다.

그래서 이 커맨드는 **반증까지 통과한 CONFIRMED만 자동 수정**한다. PLAUSIBLE은 사람이
고르고, REFUTED도 화면에 보여준다 — 무엇이 걸러졌는지 보이지 않으면 걸러진다는 사실
자체를 신뢰할 수 없기 때문이다.

밀고 싶다면 안전핀부터 건다: 라운드 상한, `--max-budget-usd`, 그리고 "수정은 하되
커밋은 사람이" 원칙.

## 6. CI로 승격하려면

PR이 열릴 때 자동 리뷰가 붙고 코멘트가 남는 형태. 이 레포에는 **아직 만들지 않았다** —
사람 손이 한 번 필요한 단계가 둘 있어서다.

1. **토큰.** 구독 계정이면 `claude setup-token`으로 장기 토큰을 만들어 레포 시크릿
   (`CLAUDE_CODE_OAUTH_TOKEN`)에 넣는다. API 키 과금을 쓸 거면 `ANTHROPIC_API_KEY`.
2. **`gh` 스코프.** 지금 이 머신의 `gh` 토큰 스코프는 `gist, read:org, repo`뿐이라
   **`.github/workflows/` 파일을 푸시하면 거부된다.** 먼저 사람이 직접
   `gh auth refresh -s workflow`를 한 번 실행해야 한다.
3. 워크플로는 `pull_request: [opened, synchronize]`에서 리뷰를 돌리고 결과를 PR
   코멘트로 남기게 한다. 로컬에서는 `gh pr view --comments`로 당겨와 반영한다.

CI 리뷰는 **로컬에만 있는 상태를 못 본다**(`.env.local`, 설치된 dev build, 시뮬레이터).
그런 결함은 여전히 로컬 `/wt:review`나 사람이 잡아야 한다. 둘은 대체가 아니라 보완이다.

## 7. `ultrareview`는 사람만 띄운다

`claude ultrareview [PR번호]` / `/code-review ultra`는 클라우드 다중 에이전트 리뷰로,
독립성과 깊이가 가장 높다. **세션 안의 모델이 대신 실행할 수 없고** 별도로 과금된다.
`/wt:review`가 애매한 판정을 많이 내놓거나 변경이 특별히 큰 PR이면, 사람이 직접
한 번 돌리는 게 가장 확실하다.
