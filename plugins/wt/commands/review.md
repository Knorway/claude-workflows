# /wt:review

구현한 세션이 자기 코드를 검토하면 자기 합리화를 그대로 물려받는다. 이 커맨드는
**문맥이 전혀 없는 리뷰어 여럿**을 병렬로 띄워 그 편향을 우회하고, 나온 지적을
**반증 담당**에게 한 번 더 거른 다음, 살아남은 것만 고친다.

원리와 비용 모델은 [`docs/review-loop.md`](../../../docs/review-loop.md).

## 인자

`$ARGUMENTS`:

- **숫자** → 그 PR을 리뷰한다 (`gh pr diff <n>`).
- **브랜치 이름** → 그 브랜치를 base로 삼는다.
- **`--quick`** → 렌즈 2개, 반증 단계 생략, 자동 수정 없음. 훑어보기용.
- **`--deep`** → 렌즈 5개, finding당 반증 3표(과반으로 판정).
- **비었으면** 기본: 현재 브랜치 vs base, 렌즈 3개, 반증 1표.

base 브랜치는 `.claude/wt.json`의 `baseBranch` → `git symbolic-ref --short
refs/remotes/origin/HEAD` 순으로 정한다(`/wt:remote-push`와 같은 규칙).

## 1. 범위 확정 — 한 번의 호출

```bash
git branch --show-current
git fetch -q origin 2>/dev/null
git diff origin/<base>...HEAD --stat -- ':(exclude)*.lock' ':(exclude)yarn.lock' ':(exclude)package-lock.json' ':(exclude)pnpm-lock.yaml' ':(exclude)go.sum'
```

PR 모드면 대신 `gh pr view <n> --json title,state,baseRefName,headRefName` 와
`gh pr diff <n> --name-only`.

**`state`가 `MERGED`(또는 `CLOSED`)면 읽기 전용으로 강등한다** — 5단계 자동 수정을
건너뛰고 보고만 한다. 리뷰어는 그 PR 시점의 옛 diff를 보는데 수정은 **지금의 워킹
트리**에 가해지므로, 이미 후속 커밋이 해결한 문제를 되돌리거나 존재하지 않는 코드를
고치려 든다. 강등했다는 사실을 보고 첫 줄에 적는다. 사용자가 명시적으로 "머지됐어도
고쳐라"라고 하면 그때만 수정한다.

**diff 원문을 절대 네 문맥에 올리지 마라.** `--stat`만 본다. 원문은 각 서브에이전트가
자기 문맥에서 읽는다 — 이게 이 커맨드의 비용을 결정하는 단 하나의 규칙이다.

변경이 없으면 "리뷰할 변경이 없다"고 말하고 **끝낸다.** 서브에이전트를 띄우지 않는다.

`--quick`이 아닌데 diff가 **200줄 미만**이면 렌즈를 2개로 줄인다. 3000줄을 넘으면
사용자에게 범위를 좁힐지(경로 한정) 먼저 묻는다.

## 2. 렌즈 병렬 fan-out

`wt:reviewer` 에이전트를 렌즈마다 하나씩, **한 메시지에 전부** 띄운다(그래야 동시에
돈다). 이름이 해석되지 않으면 `general-purpose`에 같은 프롬프트를 싣는다.

기본 3개:

1. **정확성** — 이 변경이 깨뜨리는 것. 엣지케이스, null/빈 값, 에러 경로, 경합,
   되돌아온 회귀.
2. **규약** — `CLAUDE.md`/`AGENTS.md`/`DESIGN.md`가 명시한 규칙 위반. 문서에 적힌
   것만 근거로 삼는다. 리뷰어의 취향은 근거가 아니다.
3. **보안·설정** — 비밀·키·토큰, 커밋되면 안 되는 파일, 클라이언트 번들에 인라인되는
   공개 env, 빌드·네이티브 설정에 미치는 영향.

`--deep`이면 추가:

4. **인터페이스·데이터 흐름** — 호출자/스키마/타입 계약이 어긋나는 곳, 부분 마이그레이션.
5. **중복·복잡도** — 이미 있는 함수를 다시 만든 곳, 이 diff가 도입한 불필요한 분기.

각 서브에이전트 프롬프트에 반드시 넣을 것:

- 그 렌즈의 정의(위 문장 그대로)
- **diff를 얻는 명령 원문** (`git diff origin/<base>...HEAD -- <제외패턴>` 또는
  `gh pr diff <n>`) — 내용이 아니라 명령을
- 레포 루트 경로
- "JSON 배열만 출력"

서브에이전트가 결과 없이 죽으면(도구 내부 오류 등) **그 렌즈만 한 번 재시도한다.**
두 번째도 실패하면 포기하고, 최종 보고 **첫 줄에 어느 축의 커버리지가 비었는지**
적는다. 조용히 넘어가면 사용자는 3개 렌즈가 다 돈 줄로 읽는다.

## 3. 취합 — 네가 한다

- `file` + `line`(±3줄)이 같은 지적은 하나로 합친다. 서로 다른 렌즈가 같은 곳을
  가리켰다면 그건 신호이니 severity를 올린다.
- `--quick`이면 여기서 **바로 6단계**로 간다(반증도 수정도 없음).
- `low` 중 실패 시나리오가 부실한 것은 버린다.

## 4. 반증 병렬

남은 finding마다 `wt:refuter`를 하나씩, **한 메시지에 전부** 띄운다. `--deep`이면
finding당 3개를 띄우고 **과반**으로 판정한다(CONFIRMED 2표 이상이라야 CONFIRMED).

각 프롬프트에 finding JSON 하나를 그대로 싣고, 레포 루트를 알려준다.

**돌아온 판정을 그대로 믿지 말고 기계적으로 한 번 거른다:** `verdict`가 `CONFIRMED`인데
`check`가 비어 있으면(= 실행으로 확인하지 못했으면) **`PLAUSIBLE`로 내린다.** 실측에서
반증 담당이 재현을 못 하자 규칙 기억으로 추론해 오탐을 `CONFIRMED`로 승인한 사례가
있었다 — 자동 수정의 유일한 관문이므로 이 강등은 프롬프트가 아니라 여기서 강제한다.

## 5. 수정 — CONFIRMED만

- **머지·닫힌 PR을 리뷰했다면 이 단계 전체를 건너뛴다** (1단계 참조).
- CONFIRMED만 고친다. PLAUSIBLE·REFUTED는 **손대지 않는다.**
- **최대 2라운드.** 고친 뒤 그 파일에 대해서만 1번 재검토하고, 그래도 남으면 사람에게
  넘긴다. 무한 루프로 가지 않는다.
- 고친 다음 **레포의 검증 절차를 그대로 실행한다** — 이 레포의 `CLAUDE.md`가 정한
  순서(타입체크·생성기·서버 호출 등)를 따르고, 없으면 뻔한 정적 검사만 돌린다.
- 커밋하지 않는다. 커밋·푸시는 `/wt:remote-push`의 일이다.

## 6. 보고

세 구획으로, 표 하나:

```
### 수정됨 (CONFIRMED n건)
| 파일:줄 | 무엇이 문제였나 | 어떻게 고쳤나 |

### 판단 필요 (PLAUSIBLE n건)
| 파일:줄 | 지적 | 반증이 왜 실패했나 |

### 기각 (REFUTED n건)  ← 한 줄 요약만
```

기각된 것도 **반드시 보여준다.** 무엇이 걸러졌는지 보이지 않으면 사용자가 이 커맨드를
신뢰할 근거가 없다. 마지막 줄에 렌즈 수와 반증 수를 적어 비용을 짐작할 수 있게 한다.

발견이 0건이면 표를 만들지 말고 한 문장으로 끝낸다.
