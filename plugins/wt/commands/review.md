# /wt:review

구현한 세션이 자기 코드를 검토하면 자기 합리화를 그대로 물려받는다. 이 커맨드는
**문맥이 전혀 없는 리뷰어 여럿**을 병렬로 띄워 그 편향을 우회하고, 나온 지적을
**반증 담당**에게 한 번 더 거른 다음, 살아남은 것만 고친다.

원리와 비용 모델은 [`docs/review-loop.md`](../../../docs/review-loop.md).

**모드는 하나다.** 렌즈 수도 반증 표 수도 플래그가 아니라 **diff에서 유도한다** —
사람이 매번 "이번엔 얼마나 세게"를 고르게 하면 그 판단이 곧 청구서가 되고, 실측상
그 선택은 diff만 보면 기계적으로 정해진다.

**이 커맨드는 테스트를 *쓴다*. 돌리는 것은 `wt-verify`의 일이다.** 리뷰와 테스트 작성이
한 커맨드에 있는 것은 정보가 여기에만 있기 때문이고(diff·규약·무맥락 시점을 이미 만들어
값을 치렀다), 무엇보다 **빨간 테스트가 곧 영속하는 `check`**여서 finding과의 접합이
여기서만 가능하기 때문이다. 대신 결합은 **단방향**이어야 한다 — 리뷰가 테스트를 만들
수는 있어도, 테스트 스위트가 리뷰에 의존해서는 안 된다. 테스트는 러너가 그냥 돌릴 수
있는 평범한 파일로 남는다.

## 인자

`$ARGUMENTS`:

- **숫자** → 그 PR을 리뷰한다 (`gh pr diff <n>`).
- **브랜치 이름** → 그 브랜치를 base로 삼는다.
- **비었으면** 현재 브랜치 vs base.

base 브랜치는 `.claude/wt.json`의 `baseBranch` → `git symbolic-ref --short
refs/remotes/origin/HEAD` 순으로 정한다(`/wt:remote-push`와 같은 규칙).

## 1. 범위 확정 — 한 번의 호출

```bash
git branch --show-current
git fetch -q origin 2>/dev/null
BASE_AT=$(git merge-base origin/<base> HEAD)
git diff $BASE_AT --stat -- ':(exclude)*.lock' ':(exclude)*.lockb' ':(exclude)*-lock.json' ':(exclude)*-lock.yaml' ':(exclude)npm-shrinkwrap.json' ':(exclude)go.sum'
git status --porcelain -uall
```

**`...HEAD`가 아니라 merge-base부터 워킹 트리까지다.** 5단계가 "커밋하지 않는다"이므로
**이 커맨드가 만든 수정은 정의상 커밋되지 않은 채로 존재**하고, `...HEAD`로 잡으면
재호출 시 그게 안 보인다. 그리고 `/wt:remote-push`는 `git add -A`로 워킹 트리 전부를
커밋하므로, 범위를 커밋된 것으로 좁히면 **리뷰되지 않은 파일이 `review=ok`를 달고
나간다.** 리뷰 범위는 푸시 범위와 같아야 한다.

`git diff` 계열은 **추적되지 않는 새 파일을 보여주지 않는다.** 그래서 `git status`가
따로 필요하다. untracked는 서브에이전트에 **경로만** 넘기고(내용은 각자 열게 한다),
gitignore된 것은 제외한다. 수십 개가 나오면 먼저 사용자에게 정리할지 묻는다.

PR 모드면 대신 `gh pr view <n> --json title,state,baseRefName,headRefName` 와
`gh pr diff <n> --name-only`.

**`state`가 `MERGED`/`CLOSED`면 읽기 전용으로 강등한다** — 5단계를 건너뛰고 보고만 하며
7단계 기록도 남기지 않는다. 리뷰어는 옛 diff를 보는데 수정은 지금의 워킹 트리에
가해지기 때문이다. 강등 사실을 보고 첫 줄에 적는다.

**diff 원문을 절대 네 문맥에 올리지 마라.** `--stat`만 본다. 원문은 각 서브에이전트가
자기 문맥에서 읽는다 — 이게 이 커맨드의 비용을 결정하는 단 하나의 규칙이다.

변경이 없으면 "리뷰할 변경이 없다"고 말하고 **끝낸다.** 서브에이전트를 띄우지 않는다.
3000줄을 넘으면 사용자에게 범위를 좁힐지(경로 한정) 먼저 묻는다.

### 무엇을 띄울지 여기서 정한다

`--stat`과 매니페스트만 보고 정한다. diff 원문은 여전히 안 읽는다.

| 서브에이전트 | 띄우는 조건 |
| --- | --- |
| 렌즈 1·2·3 (정확성/규약/보안) | **항상**. 단 diff가 200줄 미만이면 정확성·규약 둘만 |
| 렌즈 4 (인터페이스·데이터 흐름) | `--stat`의 파일이 공개 계약을 건드릴 때 — `export`/`interface`/`type`/`enum`/스키마/마이그레이션/`.proto`/`.sql` |
| **테스트 작성자** | **테스트 러너가 감지될 때** (아래) |

테스트 러너 감지는 매니페스트로 한다 — 경로 패턴(`*.test.*`, `spec/`)보다 정확하다.
실측에서 경로 패턴은 `fixtures/` 때문에 파일 수준 오검출이 컸고, 단언 줄 세기는
영어 산문의 `should`에 걸렸다. `package.json`의 `scripts.test`·devDeps(vitest/jest/
playwright/mocha), `Cargo.toml`의 `[dev-dependencies]`, `go.mod`, `pyproject.toml`의
pytest, `.github/workflows/*`의 테스트 잡, `*.bats` — 이 중 하나라도 있으면 감지다.
**없으면 테스트 작성자를 아예 띄우지 않는다.**

## 2. 병렬 fan-out — 렌즈 + 테스트 작성자

`wt:reviewer`를 렌즈마다 하나씩, `wt:test-writer`를 하나(조건 충족 시), **한 메시지에
전부** 띄운다(그래야 동시에 돈다). 이름이 해석되지 않으면 `general-purpose`에 같은
프롬프트를 싣는다.

1. **정확성** — 이 변경이 깨뜨리는 것. 엣지케이스, null/빈 값, 에러 경로, 경합,
   되돌아온 회귀.
2. **규약** — `CLAUDE.md`/`AGENTS.md`/`DESIGN.md`가 명시한 규칙 위반. 문서에 적힌
   것만 근거로 삼는다. 리뷰어의 취향은 근거가 아니다.
   **이 diff가 그 문서들 자체를 고쳤다면 그것도 검토 대상이다** — 코드가 규칙을 어긴
   것인지, 규칙이 코드를 따라가며 사후 정당화된 것인지 구분해서 판정하게 한다.
3. **보안·설정** — 비밀·키·토큰, 커밋되면 안 되는 파일, 클라이언트 번들에 인라인되는
   공개 env, 빌드·네이티브 설정에 미치는 영향.
4. **인터페이스·데이터 흐름** — 호출자/스키마/타입 계약이 어긋나는 곳, 부분 마이그레이션.
   *(조건부)* 이 렌즈는 **"무엇이 없는지"를 보는 몇 안 되는 통로**라 조건이 맞으면 아깝지 않다.

「중복·복잡도」 렌즈는 **의도적으로 없다.** 정확성 렌즈가 요구하는 것(null/빈 값 가드)과
정면으로 대립하는 축이라, 결판낼 근거가 루프 안에 없는 채로 라운드마다 가드를
넣었다 뺐다 하는 진동을 만든다.

각 서브에이전트 프롬프트에 반드시 넣을 것:

- 그 렌즈의 정의(위 문장 그대로)
- **diff를 얻는 명령 원문**(1단계의 `git diff $BASE_AT -- <제외패턴>` 또는
  `gh pr diff <n>`)과 untracked 경로 목록 — 내용이 아니라 명령을
- 레포 루트 경로
- **커밋되지 않은 변경이 섞여 있다는 사실**
- "JSON 배열만 출력"

서브에이전트가 결과 없이 죽으면(도구 내부 오류 등) **그것만 한 번 재시도한다.
반증 담당도 같다.** 두 번째도 실패하면 포기하고, 최종 보고 **첫 줄에 어느 축의
커버리지가 비었는지** 적는다. 조용히 넘어가면 사용자는 전부 돈 줄로 읽는다.

## 3. 취합 — 네가 한다

- `file` + `line`(±3줄)이 같은 지적은 하나로 합친다. 서로 다른 렌즈가 같은 곳을
  가리켰다면 그건 신호이니 severity를 올린다.
- **테스트 작성자가 돌려준 빨간 테스트는 finding으로 편입한다.** 이미 실행으로
  확인된 것이므로 `check`가 비어 있지 않다 — 4단계에서 강등되지 않는다.
- **테스트 작성자의 `invalid_tests`도 finding으로 편입하되, `check`가 있는 것만.**
  없으면 버린다 — 4단계의 기계적 강등과 같은 기준을 앞당겨 적용하는 것이다. "이 단언은
  약해 보인다"는 인상은 취향이고, **공허함을 보이는 명령**이 있어야 결함이다.
  이 편입이 5단계 테스트 래칫의 예외 경로를 여는 유일한 통로다.
- `low` 중 실패 시나리오가 부실한 것은 버린다.

## 4. 반증 병렬

남은 finding마다 `wt:refuter`를 하나씩, **한 메시지에 전부** 띄운다. **finding당 1표.**
같은 기반 모델을 여러 표 쌓아도 오차가 상관되어 표 수만큼 정확해지지 않는다 — 정확도는
표가 아니라 아래 기계적 관문에서 나온다.

각 프롬프트에 finding JSON 하나를 그대로 싣고, 레포 루트를 알려준다.

**돌아온 판정을 그대로 믿지 말고 기계적으로 거른다.** 둘 다 프롬프트가 아니라 여기서
강제한다:

- `verdict`가 `CONFIRMED`인데 **`check`가 비어 있으면** `PLAUSIBLE`로 내린다.
  실측에서 반증 담당이 재현을 못 하자 규칙 기억으로 추론해 오탐을 승인한 사례가 있었다.
- `check`에 **워킹 트리를 바꾸는 명령**이 보이면(리다이렉트 `>`·`>>`, `sed -i`, `tee`,
  `git` 변경 동사) `PLAUSIBLE`로 내린다. 소스를 고쳐놓고 "확인했다"고 하는 것은 확인이
  아니라 **커밋되지 않은 사용자 코드에 남을 수 있는 변경**이다.

## 5. 수정 — CONFIRMED만

- **머지·닫힌 PR이면 이 단계 전체를 건너뛴다** (1단계).
- CONFIRMED만 고친다. PLAUSIBLE·REFUTED는 **손대지 않는다.**
- **수정 범위는 finding이 지목한 지점을 넘지 않는다.** 넘었으면 어느 파일을 왜 건드렸는지
  6단계에 적는다.
- **규약 문서(`CLAUDE.md`/`AGENTS.md`/`DESIGN.md`)는 자동 수정하지 않는다.** 이 셋은
  다음 라운드 규약 렌즈의 **유일한 증거 기반**이라(`wt:reviewer` 절차 2), 여기 착지한
  틀린 문장이 다음 라운드에 근거가 되고 그 다음 라운드에 코드가 거기 맞춰진다 — 두
  라운드 만에 날조가 사실이 된다. 고쳐야 한다고 판단했으면 **적용하지 말고 제안 diff
  그대로 6단계에** 싣는다.
- **검증을 무르게 하는 수정은 하지 않는다.** 아래 둘은 적용하지 말고, 규약 문서와 같은
  방식으로 제안 diff 그대로 6단계에 싣는다.
  - 기존 테스트의 **단언 삭제·약화**, `.skip`/`.only`/`xit`/`test.todo` 추가
  - **러너 설정** 변경 — `vitest.config.*`, `jest.config.*`, `playwright.config.*`,
    `pytest.ini`/`pyproject.toml`의 pytest 절, `.github/workflows/*`, `Makefile`의 test
    타깃. 특히 `include`/`exclude`/`testMatch`, `timeout`, `retries`, `continue-on-error`

  **예외는 하나뿐이다: 그 테스트 파일 자체를 `file`로 지목한 CONFIRMED finding이 있으면
  허용한다.** 공허한 단언을 고치는 것은 정당한 수정이고, 그 판정은 이미 반증까지
  통과했다. 반대로 프로덕션 결함을 고치다 테스트가 줄어들었다면 그건 정의상 바로 위
  "수정 범위는 finding이 지목한 지점을 넘지 않는다"를 어긴 것이다.

  왜 여기만 유별난가: 다른 오판은 검증 사다리가 빨갛게 잡아주지만, 이 부류는 **사다리
  자체를 무르게 만들어서** 초록이 된다. 자기를 검사할 도구를 자기가 고치는 것이라
  관측이 스스로를 못 잡는다.
- 고친 다음 **그 파일만 한 번 재검토한다.** 두 가지를 지켜라:
  - **맥락 없이.** 원래 finding도 "어떻게 고쳤는지"도 넘기지 않는다. 수정 의도를 넘기면
    리뷰어는 "코드가 그 의도대로인가"를 묻게 되는데, 실측에서 잡혀야 했던 결함은
    **의도 자체가 틀린** 경우였다. 무맥락 리뷰어만 "이 전제가 참인가"를 묻는다.
  - **같은 `file`+`line`(±3)이 두 번째로 지적되면 자동 수정을 멈추고 사람에게 넘긴다.**
    넓힘↔좁힘 같은 반대 방향 지적을 결판낼 근거가 이 루프에 없다. 진동은 못 막아도
    감지는 싸다.
- **수정 세대는 5단계·재검토를 통틀어 최대 2회.** 무한 루프로 가지 않는다.
- **래칫 검사 — `wt-verify`보다 먼저, 기계적으로.** 위 규칙을 프롬프트에만 맡기지 않는다.

  ```bash
  git diff --numstat -- <테스트 파일 경로들> <러너 설정 파일들>
  git diff -U0 -- <테스트 파일 경로들> | grep '^+' | grep -vE '^\+\+\+' \
    | grep -nE '\.(skip|only|todo)\b|^\+[[:space:]]*x(it|describe)\b'
  ```

  위반은 셋 중 하나라도 참일 때다:

  - 삭제 열(둘째 칸)이 `0`이 아닌 테스트 파일 중 **CONFIRMED finding의 `file` 집합에
    없는 것**이 있다
  - 러너 설정 파일이 하나라도 바뀌었다
  - 둘째 명령이 무언가를 출력했다

  **둘째 명령이 왜 따로 필요한가:** 기존 테스트를 `describe.skip(...)`으로 감싸는 것은
  줄을 하나도 지우지 않으므로 `--numstat`에 `2 0`으로, 즉 **테스트를 추가한 것과 똑같이**
  찍힌다(실측 확인). 스위트 전체를 끄는 가장 값싼 방법이 정확히 첫째 검사의 사각지대에
  있다.

  위반이면 6단계에 그 행을 그대로 싣고 7단계를 `review=human`으로 내린다.

  **되돌리지 마라.** 이건 탐지이지 롤백이 아니다 — 이 루프는 커밋되지 않은 사용자 수정을
  안고 돌기 때문에, 되돌리는 순간 리뷰와 무관한 작업까지 날아간다(리뷰어·반증 담당에게
  건 금지와 같은 이유). 지우는 대신 **보이게 만들고 게이트를 닫는다.**
- 그다음 **`wt-verify plan`** 으로 검증 사다리를 받아, **수정이 건드린 파일에 해당하는
  단계, 그리고 테스트를 새로 썼으면 테스트 단계 전부**를 직접 실행하고
  `wt-verify note <id>=…`로 결과를 남긴다. (`wt-verify`는 명령을 출력만 한다 — 실행은
  네가 한다.) **전체 스위트는 리뷰 전체에서 여기 한 번만 돈다.**
- 커밋하지 않는다. 커밋·푸시는 `/wt:remote-push`의 일이다.

## 6. 보고

```
### 수정됨 (CONFIRMED n건)
| 파일:줄 | 무엇이 문제였나 | 어떻게 고쳤나 |

### 판단 필요 (PLAUSIBLE n건)
| 파일:줄 | 지적 | 반증이 왜 실패했나 |

### 기각 (REFUTED n건)  ← 한 줄 요약만
```

기각된 것도 **반드시 보여준다.** 무엇이 걸러졌는지 보이지 않으면 사용자가 이 커맨드를
신뢰할 근거가 없다. 마지막 줄에 렌즈 수와 반증 수를 적어 비용을 짐작할 수 있게 한다.

### 이 수정이 새로 주장한 것

수정이 **주석·문서에 추가한 산문을 원문 그대로** 나열한다. 컴파일러도 테스트도 이
줄들만은 검사하지 않으므로, 패치에서 **검증받지 않은 유일한 부분**이다. 추출은 기계적으로:

```bash
git diff -U0 -- <수정한 파일들> | grep '^+' | grep -v '^+++'
```

에서 `.md` 파일의 모든 줄과, 그 외 파일의 `*` · `//` · `#`로 시작하는 줄만 남긴다.
**한 줄도 요약하거나 걸러내지 마라.** 다만 해당 finding의 `failure_scenario`에 나오지
않는 파일명·심볼을 언급하는 줄 앞에는 `⚠`를 붙인다 — 근거가 준 범위 밖을 주장한다는
뜻이다. 5단계에서 적용하지 않은 **규약 문서 제안 diff**도 여기 붙인다.
한 줄도 없으면 이 구획을 만들지 않는다.

`⚠` 판정을 **수정자가 아니라 네가** 한다는 게 핵심이다. 자기 산문을 자기가 심사하면
"내 주석은 근거 범위 안"이라는 답만 나온다.

### 테스트가 어떻게 움직였나

5단계 래칫 검사의 `git diff --numstat` 출력에서 **테스트 파일과 러너 설정 행을 그대로**
싣는다. 요약하지 말고 숫자를 그대로 보여라 — 이 표의 값은 "검증이 얼마나 무뎌졌나"를
사람이 **한 눈에 세어볼 수 있게** 하는 것이고, 산문으로 옮기는 순간 그게 사라진다.

```
추가  삭제  파일
  24     0  web/src/features/film/title.test.ts
   6     4  web/e2e/film.spec.ts        ← 삭제가 있다. 근거가 있나?
```

삭제 열이 `0`이 아닌데 그 파일을 지목한 CONFIRMED가 없는 행, 그리고 러너 설정 파일 행
앞에는 `⚠`를 붙인다. `skip`/`only` 검사가 무언가를 출력했으면 **그 줄도 원문 그대로**
싣는다 — numstat만 보면 추가와 구분되지 않기 때문이다. 적용하지 않은 **제안 diff**도
여기 붙인다. 움직임이 전혀 없으면 이 구획을 만들지 않는다.

`skip` 검사는 `list.todos` 같은 무해한 속성 접근에 걸릴 수 있다(실측: rootcam의 테스트
76건에서는 0건). 걸려도 결과는 사람이 한 번 보는 것뿐이니 **틀리는 방향이 안전하다** —
이 루프의 안전장치는 전부 이 성질을 만족해야 한다.

### 새로 쌓은 테스트

테스트 작성자가 남긴 파일과 케이스를 적는다. **빨간 것은 위 표에 finding으로 이미
올라가 있고**, 여기에는 초록으로 통과한 것 — 즉 결함은 아니지만 커버리지로 남은 것 —
과 "쓰려다 만 것과 그 이유"를 적는다.

발견이 0건이고 새 테스트도 없으면 표를 만들지 말고 한 문장으로 끝낸다.

## 7. 리뷰했다는 기록 남기기 (마지막, 필수)

보고를 마친 뒤 원장에 한 줄 남긴다. 이게 `/wt:remote-push`의 리뷰 게이트가 보는 신호이고,
동시에 PR 본문 `## 확인`에 **이 브랜치가 리뷰됐다는 사실**이 영구히 남는다.

```bash
wt-verify note review=ok:"4렌즈+테스트작성 · CONFIRMED 2건 수정, 테스트 5건 추가, REFUTED 4건"
```

**`ok`가 아니라 `human`으로 남겨야 하는 경우가 셋 있다:**

- 사람이 판단해야 할 **PLAUSIBLE이 남았을 때**
- **수정 세대 상한에 걸려 CONFIRMED가 안 고쳐진 채 남았을 때** — 실행으로 확인된 결함이
  미수정인데 `ok`가 찍히면 게이트가 가장 나쁜 경우에 거짓말한다
- **5단계 래칫 위반이 검출됐을 때** — 근거 없이 테스트가 지워졌거나 러너 설정이 넓어진
  채로 `ok`가 찍히면, 게이트가 **초록을 보증하는 도구 자체가 무뎌진 상태**를 통과시킨다.
  detail에 어느 파일에서 몇 줄이 지워졌는지 적는다

```bash
wt-verify note review=human:"PLAUSIBLE 2건 — src/map.tsx:88 경합, src/list.tsx:12 널 경로"
```

detail에는 **무엇이 어디에 남았는지 file:line**을 적는다. 그리고 **detail에 `미실행`이라는
문자열을 쓰지 마라** — `/wt:remote-push` 0단계의 `grep -v 미실행`이 줄 전체에 걸려
게이트가 막힌다.

머지·닫힌 PR을 읽기 전용으로 리뷰한 경우엔 **남기지 않는다** — 지금 워킹 트리를 검토한
것이 아니므로 게이트를 통과시켜선 안 된다.
