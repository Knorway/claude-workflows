# /wt:review

구현한 세션이 자기 코드를 검토하면 자기 합리화를 그대로 물려받는다. 이 커맨드는
**문맥이 전혀 없는 리뷰어 여럿**을 병렬로 띄워 그 편향을 우회하고, 나온 지적을
**반증 담당**에게 한 번 더 거른 다음, 살아남은 것만 고친다.

그 위에 축이 하나 더 있다. 무맥락 리뷰어는 "이 코드가 제대로 도는가"까지만 물을 수 있고,
**"애초에 이걸 했어야 했나"는 의도를 아는 개체만 물을 수 있다.** `wt:trickster`가 그
자리다 — 이 파이프라인에서 **유일하게 플랜을 읽는 개체**이고, 읽는 이유는 따르기 위해서가
아니라 뒤집기 위해서다. 그 답은 고칠 수 있는 종류가 아니므로 수정 루프에 넣지 않고
보고에만 싣는다(6단계 「악마의 질문」).

원리와 비용 모델은 [`docs/review-loop.md`](../../../docs/review-loop.md).

**이 커맨드는 대화 맥락을 요구하지 않는다.** 리뷰어와 반증 담당에게 무맥락은 요건이고,
trickster가 읽는 의도조차 대화가 아니라 **플랜 파일과 `git log`**에서 온다. 그 플랜이
착수 전에 쓰여 낡았다는 문제도 기억이 아니라 **대조**로 푼다(1단계). 그러니 새 세션에서
돌려도 같은 리뷰여야 하고, **대화의 기억을 근거로 삼는 단계가 생기면 그건 그 단계의
결함이다.** 부르기 전에 `/compact`할 이유도 없다 — 요약이 지켜줄 것이 여기에 없다.

**모드는 하나다.** 렌즈 수도 반증 표 수도 플래그가 아니라 **diff에서 유도한다** —
사람이 매번 "이번엔 얼마나 세게"를 고르게 하면 그 판단이 곧 청구서가 되고, 실측상
그 선택은 diff만 보면 기계적으로 정해진다.

**이 커맨드는 테스트를 *쓴다*. 돌리는 것은 `wt-verify`의 일이다.** 리뷰와 테스트 작성이
한 커맨드에 있는 것은 정보가 여기에만 있기 때문이고(diff·규약·무맥락 시점을 이미 만들어
값을 치렀다), 무엇보다 **빨간 테스트가 곧 영속하는 `check`**여서 finding과의 접합이
여기서만 가능하기 때문이다. 대신 결합은 **단방향**이어야 한다 — 리뷰가 테스트를 만들
수는 있어도, 테스트 스위트가 리뷰에 의존해서는 안 된다. 테스트는 러너가 그냥 돌릴 수
있는 평범한 파일로 남는다.

## 인자

`$ARGUMENTS`:

- **숫자** → 그 PR을 리뷰한다 (`gh pr diff <n>`).
- **브랜치 이름** → 그 브랜치를 base로 삼는다.
- **비었으면** 현재 브랜치 vs base.

base 브랜치는 `.claude/wt.json`의 `baseBranch` → `git symbolic-ref --short
refs/remotes/origin/HEAD` 순으로 정한다(`/wt:remote-push`와 같은 규칙).

## 1. 범위 확정 — 한 번의 호출

```bash
git branch --show-current
git fetch -q origin 2>/dev/null
BASE_AT=$(git merge-base origin/<base> HEAD)
git diff $BASE_AT --stat -- ':(exclude)*.lock' ':(exclude)*.lockb' ':(exclude)*-lock.json' ':(exclude)*-lock.yaml' ':(exclude)npm-shrinkwrap.json' ':(exclude)go.sum'
git status --porcelain -uall
```

**`...HEAD`가 아니라 merge-base부터 워킹 트리까지다.** 5단계가 "커밋하지 않는다"이므로
**이 커맨드가 만든 수정은 정의상 커밋되지 않은 채로 존재**하고, `...HEAD`로 잡으면
재호출 시 그게 안 보인다. 그리고 `/wt:remote-push`는 `git add -A`로 워킹 트리 전부를
커밋하므로, 범위를 커밋된 것으로 좁히면 **리뷰되지 않은 파일이 `review=ok`를 달고
나간다.** 리뷰 범위는 푸시 범위와 같아야 한다.

`git diff` 계열은 **추적되지 않는 새 파일을 보여주지 않는다.** 그래서 `git status`가
따로 필요하다. untracked는 서브에이전트에 **경로만** 넘기고(내용은 각자 열게 한다),
gitignore된 것은 제외한다. 수십 개가 나오면 먼저 사용자에게 정리할지 묻는다.

PR 모드면 대신 `gh pr view <n> --json title,state,baseRefName,headRefName` 와
`gh pr diff <n> --name-only`.

**`state`가 `MERGED`/`CLOSED`면 읽기 전용으로 강등한다** — 5단계를 건너뛰고 보고만 하며
7단계 기록도 남기지 않는다. 리뷰어는 옛 diff를 보는데 수정은 지금의 워킹 트리에
가해지기 때문이다. 강등 사실을 보고 첫 줄에 적는다. **이때는 쓰기를 가진 둘도 읽기
전용이다** — `wt:test-writer`는 아예 띄우지 않고, `wt:trickster`에게는 "파일을 쓰지 말고
`premise`만 돌려라"라고 넘긴다. 옛 diff를 근거로 지금 트리에 파일을 남기는 것은 5단계를
건너뛰는 이유와 같은 이유로 틀렸고, 전제 질문만은 옛 diff에서도 그대로 유효하다.

**diff 원문을 절대 네 문맥에 올리지 마라.** `--stat`만 본다. 원문은 각 서브에이전트가
자기 문맥에서 읽는다 — 이게 이 커맨드의 비용을 결정하는 단 하나의 규칙이다.

변경이 없으면 "리뷰할 변경이 없다"고 말하고 **끝낸다.** 서브에이전트를 띄우지 않는다.
3000줄을 넘으면 사용자에게 범위를 좁힐지(경로 한정) 먼저 묻는다.

### 플랜을 지금 상태로 맞춘다 — fan-out 전에

**이 파이프라인에서 대화에만 있고 디스크에 없는 것은 하나뿐이다: 플랜을 세운 뒤 뒤집힌
결정들.** diff는 git에, 리뷰 기록은 원장에, 의도는 플랜 파일에 있는데, **플랜은 착수
전에 쓰였다.** trickster는 이 커맨드에서 유일하게 의도를 읽는 개체이고 그 의도를 플랜
파일에서 받으므로, 갱신하지 않으면 **이미 답이 나온 질문을 공격한다** — 그리고 그것을
결판낼 근거가 이 루프 안에 없다(수정 루프의 진동을 막는 이유와 같다).

플랜 파일 경로는 **`/wt:remote-push` 5단계의 「plan file rule」**로 정한다. 파일이 없으면
(플랜 모드를 안 거친 작업) 이 절을 통째로 건너뛴다 — 그때는 `git log`가 의도의 기록이고,
trickster에게 가는 것도 그것뿐이다.

**네가 기억으로 쓰지 마라. 서브에이전트 하나에게 대조시킨다.** 어긋남은 기억이 아니라
**플랜 파일과 트리의 차이**이고, 그건 읽으면 나온다. 그리고 이탈을 저지른 세션이 자기
이탈을 적으면 변명이 같이 붙는다 — "불가피했다"는 이 커맨드가 애초에 우회하려는 그
자기합리화다. trickster에게 필요한 것은 **표적이지 변명이 아니다.**

`wt:reviewer` 하나를 **fan-out과 같이** 띄운다(렌즈로 세지 않는다). 프롬프트에 넣는 것:
플랜 파일 **경로**, 1단계의 diff 명령 원문, untracked 경로 목록, 레포 루트.
**플랜 내용도 diff 원문도 네 문맥에 올리지 마라** — 그쪽이 자기 문맥에서 읽는다.

시키는 것: **플랜이 말한 것과 트리가 실제로 한 것이 어긋나는 지점만** 한 줄씩. 넷 중 하나다.

1. 플랜이 하겠다고 한 것 중 **안 한 것**
2. **다르게 한 것** — 플랜의 방법 대신 다른 방법이 트리에 있는 것
3. 플랜에 없는데 **한 것**
4. 플랜이 근거로 든 **사실이 트리와 다른 것** (수치·파일 수·가정)

**「왜」는 묻지 않는다.** 이유는 트리에 없고, 있다 해도 trickster가 공격할 대상은
이유가 아니라 어긋남 자체다. 한 줄은 「플랜: … / 트리: …」 꼴이면 족하다.

돌아온 줄들을 **네가 읽지 말고 그대로** 파일 끝에 붙인다:

```bash
grep -q '^## 실제로는' "$PLAN" || printf '\n## 실제로는 이렇게 갔다\n' >> "$PLAN"
printf '%s\n' "$LINES" >> "$PLAN"
```

지켜야 할 것 넷:

- **덧붙이기만 한다. 기존 줄은 고치지 마라.** 플랜은 그때의 판단 기록이고, 뒤집혔다는
  사실 자체가 trickster에게 가장 값진 재료다 — 고쳐버리면 "왜 그렇게 생각했었나"가
  사라지고 뒤집힌 적 없는 매끈한 플랜만 남는다.
- **섹션이 이미 있으면 그 아래에 이어 붙인다.** 재호출이 표준이므로 중복은
  대조 개체가 같은 어긋남을 다시 보고할 때 생긴다 — 붙이기 전 같은 줄이 이미 있으면 건너뛴다.
- **어긋남이 없으면 아무것도 쓰지 않는다.** 빈 섹션도 "계획대로 갔다"도 쓰지 마라 —
  다음 회차의 이 검사에 노이즈로 남는다.
- **한 항목 한 줄, 최대 10줄.** 여기 쓰는 것은 서사가 아니라 표적이다.

**이 절에 대화가 한 글자도 들어가지 않는 것이 요건이다.** 그래서 `/wt:review`는 어디서
돌려도 같은 리뷰이고, 이 커맨드를 부르기 전에 세션을 `/compact`할 이유가 없다 — 요약이
지켜줄 것이 여기에 없다. 구현한 세션이 뒤집힌 이유까지 알고 있고 그게 값지다고 판단되면,
**그건 요약에 맡길 것이 아니라 지금 플랜 파일에 한 줄 적을 것**이다.

### 무엇을 띄울지 여기서 정한다

`--stat`과 매니페스트만 보고 정한다. diff 원문은 여전히 안 읽는다.

| 서브에이전트 | 띄우는 조건 |
| --- | --- |
| 렌즈 1·2·3 (정확성/규약/보안) | **항상**. 단 diff가 200줄 미만이면 정확성·규약 둘만 |
| 렌즈 4 (인터페이스·데이터 흐름) | `--stat`의 파일이 공개 계약을 건드릴 때 — `export`/`interface`/`type`/`enum`/스키마/마이그레이션/`.proto`/`.sql` |
| **테스트 작성자** | **테스트 러너가 감지될 때** (아래) |
| **trickster** | **항상**. diff 크기와 무관하다 |
| **플랜 대조** (위 절) | **플랜 파일이 있을 때만.** 렌즈로 세지 않는다 |

**trickster만 diff 크기 게이트가 없다.** 작은 diff에서 렌즈를 줄이는 이유는 렌즈끼리 같은
줄을 두 번 읽는 중복 비용인데, trickster는 축이 달라 겹칠 것이 없다 — 악의적 입력과 "애초에
이걸 했어야 했나"는 세 줄짜리 변경에서도 물을 수 있고, 실제로 작은 변경일수록 그 질문이
싸게 먹힌다. 러너가 없으면 테스트는 못 쓰지만 질문은 그대로 한다.

테스트 러너 감지는 매니페스트로 한다 — 경로 패턴(`*.test.*`, `spec/`)보다 정확하다.
실측에서 경로 패턴은 `fixtures/` 때문에 파일 수준 오검출이 컸고, 단언 줄 세기는
영어 산문의 `should`에 걸렸다. `package.json`의 `scripts.test`·devDeps(vitest/jest/
playwright/mocha), `Cargo.toml`의 `[dev-dependencies]`, `go.mod`, `pyproject.toml`의
pytest, `.github/workflows/*`의 테스트 잡, `*.bats` — 이 중 하나라도 있으면 감지다.
**없으면 테스트 작성자를 아예 띄우지 않는다.**

## 2. 병렬 fan-out — 렌즈 + 테스트 작성자 + trickster

`wt:reviewer`를 렌즈마다 하나씩, `wt:test-writer`를 하나(조건 충족 시), `wt:trickster`를
하나, **한 메시지에 전부** 띄운다(그래야 동시에 돈다). 이름이 해석되지 않으면
`general-purpose`에 같은 프롬프트를 싣는다.

1. **정확성** — 이 변경이 깨뜨리는 것. 엣지케이스, null/빈 값, 에러 경로, 경합,
   되돌아온 회귀.
2. **규약** — `CLAUDE.md`/`AGENTS.md`/`DESIGN.md`가 명시한 규칙 위반. 문서에 적힌
   것만 근거로 삼는다. 리뷰어의 취향은 근거가 아니다.
   **이 diff가 그 문서들 자체를 고쳤다면 그것도 검토 대상이다** — 코드가 규칙을 어긴
   것인지, 규칙이 코드를 따라가며 사후 정당화된 것인지 구분해서 판정하게 한다.
   여기에 **문서에 안 적혀 있어도 근거가 되는 규칙이 하나 있다**: 그 세 문서는 **파일당
   200줄 내외**이고, **코드를 읽으면 알 수 있는 것을 적지 않는다.** 이 diff가 그 셋 중
   하나를 200줄 너머로 밀었거나, 코드를 읽으면 알 수 있는 문장을 새로 적었으면 그것도
   결함이다 — 이 문서들은 이 렌즈의 **유일한 증거 기반**이라, 부풀면 다음 라운드의 판정
   근거가 통째로 잡음이 된다. 예산은 `PostToolUse` 훅(`scripts/claude-md-budget.sh`)과
   `/wt:remote-push` 0.5단계가 같이 지킨다.
3. **보안·설정** — 비밀·키·토큰, 커밋되면 안 되는 파일, 클라이언트 번들에 인라인되는
   공개 env, 빌드·네이티브 설정에 미치는 영향.
4. **인터페이스·데이터 흐름** — 호출자/스키마/타입 계약이 어긋나는 곳, 부분 마이그레이션.
   *(조건부)* 이 렌즈는 **"무엇이 없는지"를 보는 몇 안 되는 통로**라 조건이 맞으면 아깝지 않다.

「중복·복잡도」 렌즈는 **의도적으로 없다.** 정확성 렌즈가 요구하는 것(null/빈 값 가드)과
정면으로 대립하는 축이라, 결판낼 근거가 루프 안에 없는 채로 라운드마다 가드를
넣었다 뺐다 하는 진동을 만든다.

각 서브에이전트 프롬프트에 반드시 넣을 것:

- 그 렌즈의 정의(위 문장 그대로)
- **diff를 얻는 명령 원문**(1단계의 `git diff $BASE_AT -- <제외패턴>` 또는
  `gh pr diff <n>`)과 untracked 경로 목록 — 내용이 아니라 명령을
- 레포 루트 경로
- **커밋되지 않은 변경이 섞여 있다는 사실**
- "JSON 배열만 출력"

**trickster 프롬프트에만 추가로 들어가는 것**(다른 개체에는 절대 주지 마라 — 무맥락이
그쪽의 자산이다):

- **플랜 파일 경로**와 `git log origin/<base>..HEAD --format='%s%n%b'`. PR 모드면
  `gh pr view <n> --json body`도. 플랜은 **경로만** 넘긴다 — 내용을 네 문맥에 올리지 마라
  (`/wt:remote-push` 5단계가 `cat`으로 넘기는 것과 같은 이유). 위치는 **그쪽 5단계의
  「plan file rule」**을 그대로 쓴다 — mtime만 보면 **이 fan-out이 방금 띄운 서브에이전트의
  플랜 파일**을 집는다(같은 디렉터리에 `-agent-<id>` 이름으로 쌓인다). 1단계에서 이미
  경로를 정해뒀으니 여기서는 그 값을 쓰기만 한다.
- **의도는 검증 기준이 아니라 공격 대상**이라는 문장
- `wt:test-writer`도 **동시에** 돈다는 사실과, 그래서 새 파일 basename에 `hostile`을 넣고
  기존 파일은 건드리지 않는다는 규약(에이전트 정의에도 있지만 여기서 한 번 더 못 박는다 —
  이건 두 개체가 같은 순간 같은 트리에 쓰는 문제라 프롬프트에서 빠지면 조용히 덮어쓴다)

서브에이전트가 결과 없이 죽으면(도구 내부 오류 등) **그것만 한 번 재시도한다.
반증 담당도 같다.** 두 번째도 실패하면 포기하고, 최종 보고 **첫 줄에 어느 축의
커버리지가 비었는지** 적는다. 조용히 넘어가면 사용자는 전부 돈 줄로 읽는다.

## 3. 취합 — 네가 한다

- `file` + `line`(±3줄)이 같은 지적은 하나로 합친다. 서로 다른 렌즈가 같은 곳을
  가리켰다면 그건 신호이니 severity를 올린다.
- **테스트 작성자와 trickster가 돌려준 빨간 테스트는 finding으로 편입한다.** 이미 실행으로
  확인된 것이므로 `check`가 비어 있지 않다 — 4단계에서 강등되지 않는다. 둘의
  `findings`·`coverage` 스키마는 같으므로 그냥 합치면 된다.
- **trickster의 `premise`는 finding이 아니다.** 4단계(반증)와 5단계(수정)에 **넣지 마라.**
  반증할 `file:line`이 없고 자동 수정할 대상도 없다 — 전제를 코드로 고칠 수 있었으면 그건
  애초에 전제 질문이 아니다. 6단계 보고로 곧장 간다.
- **테스트 작성자의 `invalid_tests`도 finding으로 편입하되, `check`가 있는 것만.**
  없으면 버린다 — 4단계의 기계적 강등과 같은 기준을 앞당겨 적용하는 것이다. "이 단언은
  약해 보인다"는 인상은 취향이고, **공허함을 보이는 명령**이 있어야 결함이다.
  이 편입이 5단계 테스트 래칫의 예외 경로를 여는 유일한 통로다.
- `low` 중 실패 시나리오가 부실한 것은 버린다.

## 4. 반증 병렬

남은 finding마다 `wt:refuter`를 하나씩, **한 메시지에 전부** 띄운다. **finding당 1표.**
같은 기반 모델을 여러 표 쌓아도 오차가 상관되어 표 수만큼 정확해지지 않는다 — 정확도는
표가 아니라 아래 기계적 관문에서 나온다.

각 프롬프트에 finding JSON 하나를 그대로 싣고, 레포 루트를 알려준다.

**돌아온 판정을 그대로 믿지 말고 기계적으로 거른다.** 둘 다 프롬프트가 아니라 여기서
강제한다:

- `verdict`가 `CONFIRMED`인데 **`check`가 비어 있으면** `PLAUSIBLE`로 내린다.
  실측에서 반증 담당이 재현을 못 하자 규칙 기억으로 추론해 오탐을 승인한 사례가 있었다.
- `check`에 **워킹 트리를 바꾸는 명령**이 보이면(리다이렉트 `>`·`>>`, `sed -i`, `tee`,
  `git` 변경 동사) `PLAUSIBLE`로 내린다. 소스를 고쳐놓고 "확인했다"고 하는 것은 확인이
  아니라 **커밋되지 않은 사용자 코드에 남을 수 있는 변경**이다.

### PLAUSIBLE 분류 — 세 갈래

반증 담당은 재현하지 못하면 `CONFIRMED`를 줄 수 없으므로 **PLAUSIBLE은 예외가 아니라
기본값에 가깝다** — 전부 사람에게 넘기면 모든 푸시가 멈춘다(근거는 `docs/review-loop.md` §5).
위 강등을 마친 **직후**, 남은 PLAUSIBLE마다 아래를 **순서대로** 묻고 처음 걸리는 갈래에 넣는다.

1. **사람 목록에 해당하는가** → 사람에게 묻는다 (6단계 「사람 판단 필요」 + 7단계 `human`)
2. **이 지적이 오탐이어도 수정이 하는 일이 없는가** → 자동 수정 (5단계)
3. 그 외 → **미수정**, 6단계에 보고만 (7단계는 `ok`)

**사람 목록을 먼저 묻는다.** 위험한 경로에서는 "무해하다"는 판단 자체가 못 미덥고, 순서가
반대면 결제·마이그레이션 경로에 가드 한 줄이 조용히 들어간다.

**2번의 기준은 한 문장이다 — "이 지적이 틀렸다면 이 수정은 아무 일도 하지 않아야 한다."**
널 가드, 경계 보정, 이른 반환, 에러 경로 보강처럼 **원래 성립하던 입력에는 같은 결과**를
주는 것이 여기 들어간다. 아래를 **전부** 만족해야 한다:

- 수정이 finding이 지목한 `file`의 지목 지점을 넘지 않는다(5단계 범위 규칙과 같다)
- 공개 계약(`export`/타입/스키마/라우트/CLI 인자)을 바꾸지 않는다
- 5단계의 자동 수정 금지 목록(규약 문서, 테스트 파일·러너 설정)에 닿지 않는다
- 6단계 표의 **「오탐이어도 무해한 이유」를 한 문장으로 쓸 수 있다** — 못 쓰면 3번이다

**사람 목록은 이게 전부다.** 판단이 애매하면 사람 목록이 아니라 **3번(미수정)**이다 —
질문이 기본값으로 돌아가면 이 분류가 무의미해진다.

- **육안** — UI 렌더링·레이아웃·애니메이션·문구처럼 초록/빨강으로 판별되지 않는 것
- **되돌릴 수 없는 것** — DB 스키마·마이그레이션, 데이터 삭제·이관, 결제, 외부 발송
- **자격증명·접근** — 시크릿·토큰, 인증·인가 경로, CORS·CSP 같은 접근 정책
- **배포·CI 설정** — 로컬 초록이 프로덕션 초록을 보장하지 않는 것
- **공개 계약 파손** — 호출자가 이 레포 밖에 있을 수 있는 export·스키마·API
- **진동** — 같은 `file`+`line`(±3)이 반대 방향으로 두 번 지적된 것 (5단계)
- **래칫 위반**, **수정 세대 상한에 걸려 미수정으로 남은 CONFIRMED** (5단계)

## 5. 수정 — CONFIRMED + 무해한 PLAUSIBLE

- **머지·닫힌 PR이면 이 단계 전체를 건너뛴다** (1단계).
- CONFIRMED는 전부 고친다. PLAUSIBLE은 **4단계에서 2번으로 분류된 것만** 고친다. 나머지
  PLAUSIBLE과 REFUTED는 **손대지 않는다.**
- **PLAUSIBLE 수정에도 아래 규칙이 전부 그대로 걸린다** — 범위 제한, 규약 문서 금지, 검증
  무르게 금지, 무맥락 재검토, 세대 상한, 래칫 검사. 근거가 약한 쪽에 규칙을 풀 이유가 없다.
- **수정 범위는 finding이 지목한 지점을 넘지 않는다.** 넘었으면 어느 파일을 왜 건드렸는지
  6단계에 적는다.
- **규약 문서(`CLAUDE.md`/`AGENTS.md`/`DESIGN.md`)는 자동 수정하지 않는다.** 이 셋은
  다음 라운드 규약 렌즈의 **유일한 증거 기반**이라(`wt:reviewer` 절차 2), 여기 착지한
  틀린 문장이 다음 라운드에 근거가 되고 그 다음 라운드에 코드가 거기 맞춰진다 — 두
  라운드 만에 날조가 사실이 된다. 고쳐야 한다고 판단했으면 **적용하지 말고 제안 diff
  그대로 6단계에** 싣는다.
- **검증을 무르게 하는 수정은 하지 않는다.** 아래 둘은 적용하지 말고, 규약 문서와 같은
  방식으로 제안 diff 그대로 6단계에 싣는다.
  - 기존 테스트의 **단언 삭제·약화**, `.skip`/`.only`/`xit`/`test.todo` 추가
  - **러너 설정** 변경 — `vitest.config.*`, `jest.config.*`, `playwright.config.*`,
    `pytest.ini`/`pyproject.toml`의 pytest 절, `.github/workflows/*`, `Makefile`의 test
    타깃. 특히 `include`/`exclude`/`testMatch`, `timeout`, `retries`, `continue-on-error`

  **예외는 하나뿐이다: 그 테스트 파일 자체를 `file`로 지목한 CONFIRMED finding이 있으면
  허용한다.** 공허한 단언을 고치는 것은 정당한 수정이고, 그 판정은 이미 반증까지
  통과했다. **PLAUSIBLE은 이 예외를 열지 못한다** — 검증을 무르게 하는 수정은 정의상
  "오탐이어도 하는 일이 없는" 수정일 수 없으므로 애초에 4단계 2번에 들어오지 않는다. 반대로 프로덕션 결함을 고치다 테스트가 줄어들었다면 그건 정의상 바로 위
  "수정 범위는 finding이 지목한 지점을 넘지 않는다"를 어긴 것이다.

  왜 여기만 유별난가: 다른 오판은 검증 사다리가 빨갛게 잡아주지만, 이 부류는 **사다리
  자체를 무르게 만들어서** 초록이 된다. 자기를 검사할 도구를 자기가 고치는 것이라
  관측이 스스로를 못 잡는다.
- 고친 다음 **그 파일만 한 번 재검토한다.** 두 가지를 지켜라:
  - **맥락 없이.** 원래 finding도 "어떻게 고쳤는지"도 넘기지 않는다. 수정 의도를 넘기면
    리뷰어는 "코드가 그 의도대로인가"를 묻게 되는데, 실측에서 잡혀야 했던 결함은
    **의도 자체가 틀린** 경우였다. 무맥락 리뷰어만 "이 전제가 참인가"를 묻는다.
  - **같은 `file`+`line`(±3)이 두 번째로 지적되면 자동 수정을 멈추고 사람에게 넘긴다.**
    넓힘↔좁힘 같은 반대 방향 지적을 결판낼 근거가 이 루프에 없다. 진동은 못 막아도
    감지는 싸다.
- **수정 세대는 5단계·재검토를 통틀어 최대 2회.** 무한 루프로 가지 않는다.
- **래칫 검사 — `wt-verify`보다 먼저, 기계적으로.** 위 규칙을 프롬프트에만 맡기지 않는다.

  ```bash
  git diff --numstat -- <테스트 파일 경로들> <러너 설정 파일들>
  git diff -U0 -- <테스트 파일 경로들> | grep '^+' | grep -vE '^\+\+\+' \
    | grep -nE '\.(skip|only|todo)\b|^\+[[:space:]]*x(it|describe)\b'
  ```

  「테스트 파일 경로들」에는 **test-writer와 trickster가 이번 라운드에 새로 만든 파일도
  포함한다.** 새 파일은 추적되지 않아 `git diff`에 안 잡히므로 위 두 명령에는 조용하다 —
  그래서 **추가 쪽은 따로 센다**:

  ```bash
  git status --porcelain -uall | grep '^??' | awk '{print $2}'   # 새 파일 (untracked)
  ```

  거기서 테스트 파일을 골라 케이스 수를 세고, 기존 테스트 파일에 덧붙은 케이스도 함께 센다.
  **이 라운드가 더한 총 케이스 수와 그중 e2e 개수를 6단계 표에 싣는다.**

  **추가도 위반이 될 수 있다:**

  - 이 라운드의 새 케이스가 **18개**(test-writer 12 + trickster 6)를 넘었다 — 두 개체의
    프롬프트에 있는 상한이고, 지금까지 아무도 검증하지 않았다
  - 새 e2e 케이스가 **4개**(각 2개)를 넘었다
  - 레포가 `.claude/wt.json`에 `budgets.e2e.max`를 선언했는데 그 값을 넘겼다

  **왜 추가에도 관문이 필요한가:** 삭제 검사가 잡는 것은 검증이 무뎌지는 것이고, 그건 옳다.
  하지만 같은 래칫이 **한번 생긴 테스트를 지우지 못하게** 만들기 때문에, 잘못 놓인 테스트는
  남는 쪽으로만 틀린다. 그 결과 스위트는 단조 증가하고, 어느 시점부터 검증 사다리 자체가
  기능 구현보다 비싸진다. 삭제만 세는 래칫은 그 상태를 만드는 장치이지 막는 장치가 아니다.

  위반은 셋 중 하나라도 참일 때다:

  - 삭제 열(둘째 칸)이 `0`이 아닌 테스트 파일 중 **CONFIRMED finding의 `file` 집합에
    없는 것**이 있다
  - 러너 설정 파일이 하나라도 바뀌었다
  - 둘째 명령이 무언가를 출력했다

  **둘째 명령이 왜 따로 필요한가:** 기존 테스트를 `describe.skip(...)`으로 감싸는 것은
  줄을 하나도 지우지 않으므로 `--numstat`에 `2 0`으로, 즉 **테스트를 추가한 것과 똑같이**
  찍힌다(실측 확인). 스위트 전체를 끄는 가장 값싼 방법이 정확히 첫째 검사의 사각지대에
  있다.

  위반이면 6단계에 그 행을 그대로 싣고 7단계를 `review=human`으로 내린다.

  **되돌리지 마라.** 이건 탐지이지 롤백이 아니다 — 이 루프는 커밋되지 않은 사용자 수정을
  안고 돌기 때문에, 되돌리는 순간 리뷰와 무관한 작업까지 날아간다(리뷰어·반증 담당에게
  건 금지와 같은 이유). 지우는 대신 **보이게 만들고 게이트를 닫는다.**
- 그다음 **`wt-verify plan`** 으로 검증 사다리를 받아, **수정이 건드린 파일에 해당하는
  단계, 그리고 새로 쓴 테스트가 속한 단계**를 직접 실행하고
  `wt-verify note <id>=…`로 결과를 남긴다. **테스트를 썼다고 테스트 단계를 전부 돌리지
  마라** — 유닛 하나를 더했다고 브라우저 스위트를 부르는 것은, 그 스위트가 15분이면 이
  커맨드를 쓸 수 없게 만드는 규칙이다. 돌리지 않은 단계는 `미실행`으로 남고, 그게 정확한
  보고다. (`wt-verify`는 명령을 출력만 한다 — 실행은
  네가 한다.) **전체 스위트는 리뷰 전체에서 여기 한 번만 돈다.**
- 커밋하지 않는다. 커밋·푸시는 `/wt:remote-push`의 일이다.

```
### 사람 판단 필요 (n건)
| 파일:줄 | 무엇을 봐야 하나 | 왜 기계가 못 정하나 | 권고 |

### 기각 (REFUTED n건)  ← 한 줄 요약만
```

**「오탐이어도 무해한 이유」와 「왜 기계가 못 정하나」는 장식이 아니라 관문이다.**
한 문장으로 못 쓰거나
「왜 기계가 못 정하나」를 사람 목록의 항목 이름으로 못 대면, 그 행은 **미수정**으로 옮긴다.
진짜 관문은 4단계에 있고(수정 *전에* 걸린다) 여기는 백스톱이다 — **이미 적용한 수정을
「미수정」으로 옮기지는 마라.** 편집은 트리에 남아 `/wt:remote-push`의 `git add -A`에 그대로
실리므로, 라벨만 바꾸면 보고와 트리가 어긋난다. 그 경우는 「수정됨」에 남기되 마지막 열에
**「근거를 한 문장으로 못 씀」이라고 적어** 사람이 그 행을 찾을 수 있게 하고, 7단계를
`human`으로 내린다.

기각된 것도 **반드시 보여준다.** 무엇이 걸러졌는지 보이지 않으면 사용자가 이 커맨드를
신뢰할 근거가 없다. 마지막 줄에 렌즈 수와 반증 수를 적어 비용을 짐작할 수 있게 한다.
비어 있는 구획은 만들지 않는다.

### 이 수정이 새로 주장한 것

수정이 **주석·문서에 추가한 산문을 원문 그대로** 나열한다. 컴파일러도 테스트도 이
줄들만은 검사하지 않으므로, 패치에서 **검증받지 않은 유일한 부분**이다. 추출은 기계적으로:

```bash
git diff -U0 -- <수정한 파일들> | grep '^+' | grep -v '^+++'
```

에서 `.md` 파일의 모든 줄과, 그 외 파일의 `*` · `//` · `#`로 시작하는 줄만 남긴다.
**한 줄도 요약하거나 걸러내지 마라.** 다만 해당 finding의 `failure_scenario`에 나오지
않는 파일명·심볼을 언급하는 줄 앞에는 `⚠`를 붙인다 — 근거가 준 범위 밖을 주장한다는
뜻이다. 5단계에서 적용하지 않은 **규약 문서 제안 diff**도 여기 붙인다.
한 줄도 없으면 이 구획을 만들지 않는다.

`⚠` 판정을 **수정자가 아니라 네가** 한다는 게 핵심이다. 자기 산문을 자기가 심사하면
"내 주석은 근거 범위 안"이라는 답만 나온다.

### 테스트가 어떻게 움직였나

5단계 래칫 검사의 `git diff --numstat` 출력에서 **테스트 파일과 러너 설정 행을 그대로**
싣는다. 요약하지 말고 숫자를 그대로 보여라 — 이 표의 값은 "검증이 얼마나 무뎌졌나"를
사람이 **한 눈에 세어볼 수 있게** 하는 것이고, 산문으로 옮기는 순간 그게 사라진다.

```
추가  삭제  파일
  24     0  web/src/features/film/title.test.ts
   6     4  web/e2e/film.spec.ts        ← 삭제가 있다. 근거가 있나?
```

삭제 열이 `0`이 아닌데 그 파일을 지목한 CONFIRMED가 없는 행, 그리고 러너 설정 파일 행
앞에는 `⚠`를 붙인다. `skip`/`only` 검사가 무언가를 출력했으면 **그 줄도 원문 그대로**
싣는다 — numstat만 보면 추가와 구분되지 않기 때문이다. 적용하지 않은 **제안 diff**도
여기 붙인다. 움직임이 전혀 없으면 이 구획을 만들지 않는다.

`skip` 검사는 `list.todos` 같은 무해한 속성 접근에 걸릴 수 있다(실측: rootcam의 테스트
76건에서는 0건). 걸려도 결과는 사람이 한 번 보는 것뿐이니 **틀리는 방향이 안전하다** —
이 루프의 안전장치는 전부 이 성질을 만족해야 한다.

### 악마의 질문 (n건)

trickster의 `premise`를 **한 줄도 요약하지 말고** 그대로 표로 싣는다.

```
| 질문 | 왜 중요한가 | 내가 틀렸음을 보이는 방법 | 더 싼 처방 |
```

**이 구획은 고치라는 지시가 아니고, 게이트도 아니다.** 여기 있는 것은 반증되지도
수정되지도 않았다 — 반증할 `file:line`이 없기 때문이지 근거가 약해서가 아니다. 사람이
읽고 "아니다"라고 답하면 그걸로 끝나는 것이 정상이고, **한 번이라도 "그러네"가 나오면
이 개체의 값은 이미 회수된 것이다.**

trickster의 `trust_boundary` 한 줄을 이 구획 맨 위에 그대로 싣는다 — 이 라운드의 공격이
어느 경계 안에서 이뤄졌는지가 보여야 아래 질문들의 범위를 사람이 잴 수 있다.
`premise`가 0건이면 이 구획을 만들지 않는다.

### 새로 쌓은 테스트

테스트 작성자와 trickster가 남긴 파일과 케이스를 **어느 쪽이 썼는지 표시해서** 적는다
(trickster의 파일은 basename에 `hostile`이 들어 있다). **빨간 것은 위 표에 finding으로 이미
올라가 있고**, 여기에는 초록으로 통과한 것 — 즉 결함은 아니지만 커버리지로 남은 것 —
과 "쓰려다 만 것과 그 이유"를 적는다.

발견이 0건이고 새 테스트도 없으면 표를 만들지 말고 한 문장으로 끝낸다.

## 7. 리뷰했다는 기록 남기기 (마지막, 필수)

보고를 마친 뒤 원장에 한 줄 남긴다. 이게 `/wt:remote-push`의 리뷰 게이트가 보는 신호이고,
동시에 PR 본문 `## 확인`에 **이 브랜치가 리뷰됐다는 사실**이 영구히 남는다.

```bash
wt-verify note review=ok:"4렌즈+테스트작성+trickster · CONFIRMED 2건·PLAUSIBLE 3건 수정, PLAUSIBLE 2건 미수정, 테스트 5건 추가, REFUTED 4건, 악마의 질문 2건(보고만)"
```

**미수정 PLAUSIBLE이 남은 것은 `ok`다.** 그건 판단이 안 끝난 게 아니라 **판단해서 안 고친
것**이고(4단계 3번), 무엇을 왜 남겼는지는 6단계 표에 이미 있다. 건수는 detail에 적되
file:line은 보고에만 둔다 — 게이트를 통과시키는 줄에 미해결 목록을 실으면 읽는 쪽이
멈출 근거로 읽는다.

**악마의 질문은 `human` 사유가 아니다.** 건수만 detail에 적고 상태는 그대로 둔다.
전제 질문은 실행으로 확인되지 않았고 반증도 못 거쳤으므로, 그것으로 게이트를 닫으면
**모든 리뷰가 `human`이 되어** 게이트가 신호를 잃는다 — 아래 목록이 넷뿐인 것이 그 자체로
설계다. 질문이 진짜였다면 사람이 6단계 구획을 읽고 멈추면 되고, 그 판단을 기계가 대신하지
않는다. (그 질문이 **동시에** 아래 사람 목록의 항목을 가리키는 finding으로도 올라왔다면,
`human`이 되는 근거는 그 finding이지 질문이 아니다.)

**`ok`가 아니라 `human`으로 남겨야 하는 경우가 넷 있다.** 그리고 그 넷은 성격이 같지 않다 —
**PR이 생기기 전에 사람이 반드시 봐야 하는 것**과 **PR 본문에서 봐도 되는 것**이 섞여 있다.
`/wt:remote-push`가 그 구분으로 멈출지 진행할지를 정하므로, **detail의 첫 조각에 `blocking:`
또는 `notify:` 를 적는다.**

- **`blocking`** — 되돌리기 어렵거나, PR이 존재하는 것 자체가 위험한 것: **비가역 경로,
  자격증명, 배포 설정, 공개 계약 파손.** 여기서만 푸시가 멈춘다.
- **`notify`** — 나머지 전부. 사람이 봐야 하지만 **PR 본문에서 diff와 함께 보는 편이 낫다** —
  터미널 스크롤백과 달리 남고, 리뷰 맥락에 붙어 있고, 그때가 실제로 판단할 수 있는 시점이다.

넷은 그대로 두고, 어느 쪽인지만 붙인다:

- **사람 목록에 해당하는 건이 남았을 때** — **어느 단계에서 그렇게 됐는지는 묻지 않는다**
  (4단계 분류든, 5단계 재검토가 잡은 진동이든 같다). 다만 사유가 **비가역·자격증명·배포
  설정·공개 계약 파손**이면 `blocking`, **육안·진동**이면 `notify`다
- **6단계 백스톱이 걸렸을 때** — 이미 적용한 수정의 「무해한 이유」를 한 문장으로 못 썼다.
  근거를 못 대는 편집이 트리에 남아 있다는 뜻이다 → `notify` (그 편집은 diff에 있다)
- **수정 세대 상한에 걸려 CONFIRMED가 안 고쳐진 채 남았을 때** — 실행으로 확인된 결함이
  미수정인데 `ok`가 찍히면 게이트가 가장 나쁜 경우에 거짓말한다 → `notify`
- **5단계 래칫 위반이 검출됐을 때** — 근거 없이 테스트가 지워졌거나 러너 설정이 넓어진
  채로 `ok`가 찍히면, 게이트가 **초록을 보증하는 도구 자체가 무뎌진 상태**를 통과시킨다.
  detail에 어느 파일에서 몇 줄이 지워졌는지 적는다 → `notify`

```bash
wt-verify note review=human:notify:"미수정 CONFIRMED 1건 — dashboard/src/db.server.ts:88 페이지 경계"
wt-verify note review=human:blocking:"자격증명 경로 — film-upload/src/features/orders/storage.server.ts:130"
```

`human`의 detail에는 등급 뒤에 **무엇이 어디에 남았는지 file:line**을 적는다.
**둘 다 있으면 `blocking`이 이긴다** — 등급은 가장 무거운 건을 따른다.

**등급을 빼먹지 마라.** `/wt:remote-push`는 등급 없는 `human`을 **`blocking`으로 읽는다**.
안전한 쪽으로 틀리는 기본값이지만, 그 기본값에 기대면 매번 사람을 세우게 된다.

**상태가 `ok`든 `human`이든 detail에 `미실행`이라는 문자열을 쓰지 마라.** `/wt:remote-push`
0단계의 `grep -v 미실행`은 상태를 가리지 않고 **줄 전체**에 걸리고, `verify.sh`는 `ok`의
detail도 같은 줄에 괄호로 붙여 출력한다(`- review — ok (…)`). 그래서 `ok:"… 전체 스위트
미실행 …"`처럼 남기면 방금 끝낸 리뷰가 게이트에서 통째로 무효가 된다.

머지·닫힌 PR을 읽기 전용으로 리뷰한 경우엔 **남기지 않는다** — 지금 워킹 트리를 검토한
것이 아니므로 게이트를 통과시켜선 안 된다.
